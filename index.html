"A Unified Framework for Auditing, Mitigating, and Reporting Attribute Leakage in Large-Scale Face Recognition Systems"

Authors: Keshav Singla · Abhilipsa Sahoo (collaborator)
SRM Institute of Science and Technology, Kattankulathur, Chennai
Abstract

Face recognition models trained on large-scale datasets unintentionally encode sensitive demographic attributes — gender, age, ethnicity — within their embedding spaces. This work presents a unified framework for: (1) quantifying attribute leakage via adversarial inference attacks, (2) mitigating leakage through adversarial disentanglement and embedding regularization using Gradient Reversal Layers, and (3) standardized reporting via IEEE-compatible model cards and cryptographic audit logs. Validated on 200,000 samples achieving 98.4% post-mitigation demographic parity.

CASE STUDY · 01 · OBSCURA-AI · PRIVACY-PRESERVING ML
[ ADVERSARIAL DEMOGRAPHIC LEAKAGE · AUDIT → MITIGATE → REPORT ]

ObscuraAI — Auditing What a Face Recognition Model Secretly Knows

Face recognition systems are graded on accuracy. But their embeddings quietly memorize who you are — gender, age, ethnicity — even when they were never trained to. ObscuraAI is a full-stack framework that measures that hidden leakage, suppresses it, and produces a compliance-grade paper trail.

PyTorchFastAPIReact + Vitescikit-learnRechartsCryptographic Audit Logs
01 — The Problem

A face recognition model maps a photo to a high-dimensional embedding. Two faces of the same person land close together — that's the intended signal. The unintended signal: those same embeddings are linearly separable by protected attributes. An attacker who only ever sees the embeddings — never the original image — can train a simple classifier to recover gender, age bracket, or ethnicity with alarming accuracy.

Under GDPR and India's DPDP Act, that's a latent privacy violation hiding inside a "neutral" vector. Yet there was no standard tooling to quantify it, reduce it without destroying recognition accuracy, or document it for an auditor. ObscuraAI closes all three gaps in one pipeline.

02 — The Approach

A three-stage pipeline, each stage independently measurable:

  • Audit (attack it). Freeze the embeddings and train two adversarial attacker models — a Logistic Regression probe (tests linear leakage) and an MLP probe (tests non-linear leakage) — to predict each protected attribute. Leakage is scored by AUC: 0.5 = the model knows nothing, 1.0 = perfect recovery.
  • Mitigate (defend it). Apply a Gradient Reversal Layer (GRL) for adversarial disentanglement — the network is explicitly penalized for encoding protected attributes — backed by a secondary Gaussian Noise Injection sanitization layer. Recognition utility is tracked with TAR@FAR so privacy gains never silently break the model.
  • Report (prove it). Emit IEEE-style Model Cards carrying Max Demographic Disparity scores, plus tamper-evident cryptographic audit logs so a regulator can verify the result was not edited after the fact.

The headline outcome: protected-attribute leakage was driven down toward chance-level AUC while recognition utility was preserved under TAR@FAR — the privacy/utility trade-off the field usually treats as a wall. Every run ships with a signed model card, so the result is reproducible and auditable, not just a number in a notebook.

05 — Why These Engineering Decisions
  • Two attacker models, not one. LR alone only catches linear leakage; an MLP exposes leakage a linear probe would miss. Reporting both gives an honest upper bound on what an adversary could extract.
  • GRL over naïve noise. Pure noise degrades recognition accuracy fast. The Gradient Reversal Layer removes attribute signal at the representation level, so utility survives — noise is only a secondary safety net.
  • Cryptographic logs by design. Fairness claims are worthless if they can be edited after an audit. Tamper-evident logging turns "trust me" into "verify me" — the standard a real compliance review demands.

CASE STUDY · 02 · AUTOJUSTICE-AI-NEXUS · GOVTECH / PRODUCTION
[ FIR AUTOMATION · ASYNC AI PIPELINE · LEGAL-COMPLIANT BY DESIGN ]

AutoJustice AI NEXUS — Turning a Paper Bottleneck into a Production Justice Platform

In India, a delayed FIR (First Information Report) means delayed justice. The documentation burden on officers is a real chokepoint at the very first step of a case. AutoJustice automates FIR generation with AI triage and OCR — engineered from the ground up to satisfy Indian digital-evidence and privacy law, not bolt it on afterward.

FastAPIPostgreSQLRedis + CeleryGemini APITesseract OCRDocker + NGINX
01 — The Problem

Filing an FIR is manual, slow, and inconsistent. An officer transcribes a complaint, classifies it under the right legal sections, and assesses severity — by hand, under load. That latency delays case registration and, downstream, access to justice itself.

A naïve "ChatGPT for FIRs" fails instantly in this domain: anything touching legal evidence must respect Section 65B of the Indian Evidence Act, the DPDP Act for citizen data, and current BNS/IPC formatting. The hard part isn't generating text — it's generating legally admissible, auditable text at production reliability.

02 — The Approach

Treat FIR generation as an asynchronous, multi-stage pipeline rather than one blocking request — so OCR and AI inference never freeze the officer's UI:

  • Ingest. Physical documents are digitized through a Tesseract OCR pipeline; complaints enter a queue rather than a synchronous call.
  • Triage. The Gemini API categorizes each case and scores severity, suggesting the relevant legal sections for officer review — assist, not replace.
  • Process async. Celery + Redis run heavy work off the request thread; PostgreSQL holds case state with real-time status tracking.
  • Comply. Output is formatted for Section 65B / DPDP / BNS-IPC from the start, so the document is admissible by construction.

What began as "a basic HTML form" matured into a containerized, production-grade platform deployed behind NGINX. The architecture choice that mattered most: making the pipeline asynchronous — it's the difference between a demo that hangs on a large document and a system an officer can actually rely on under real caseload.

05 — Why These Engineering Decisions
  • Async-first, not request-blocking. OCR + LLM inference are slow and variable. Celery/Redis keep the officer's interface responsive while heavy work runs in the background — production reliability over demo simplicity.
  • AI assists, the officer decides. Gemini suggests categorization and sections; a human confirms. In a justice system, an unsupervised model making legal determinations is a non-starter — the design keeps accountability human.
  • Compliance as a build constraint. Section 65B / DPDP formatting is baked into the output layer, not patched in later. Admissibility can't be retrofitted onto evidence.
